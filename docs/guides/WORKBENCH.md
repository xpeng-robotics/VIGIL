# Use the workbench

For the extracted source release, start with `bash start.sh`: no package
installation is required, an available port is selected and the browser opens.
On macOS, `start.command` is an alternative. To choose a Python environment, use
`PYTHON_BIN=/path/to/python bash start.sh`.

Run `vigil ui` from the release directory. Like `bash start.sh`, it chooses an
available loopback port and prints the address. It works with the core Python installation and has no
frontend build step, external fonts, CDN assets or additional Python dependencies.

## Watch the film

For the benchmark film and hardware recordings, run `python3 scripts/media/preview.py`
from the source repository. This opens a separate, read-only player with chapter
navigation and seekable video. For individual observations and actions, use the
workbench replay below.

## Explore first

Choose **Explore a recorded run** on the overview page. Two real
`gemini-3-flash-preview` episodes are included: a successful fridge selection and
an unsuccessful toaster interaction. These saved examples do not call an API or
start a simulator. Their 50% W/B describes only this two-episode sample.

The source release also shows six film-case cards on the home page. Each opens
its own trajectory directly; individual models and feedback profiles are labeled.
The wheel retains the smaller bundled example.

Click **Replay** to move between steps or play the sequence. Each frame is the
observation **before** the action displayed next to it. The marker uses the
executed frame-pixel coordinates, even when the model supplied normalized
coordinates. The separate panels show the model decision, actual execution and
evaluator evidence. Evaluator information in this operator view is not extra
feedback supplied to the model.

Recorded assets live in `vigil/web/demo/`. Their private endpoint and run
labels have been removed. Their actions, outcomes and RGB frames are preserved;
the demo aggregate is generated by the same scorer as ordinary evaluation runs.

## Evaluate your model

1. Install the simulator extra: `python -m pip install -e ".[thor]"`, then restart
   the workbench using that Python environment. Prepare rendering as described in
   [environment setup](../reference/USAGE.md#environment-setup).
2. Open **Run an evaluation**. Enter the API format, model name, endpoint and key.
   Native providers can use their default endpoint. Expand advanced settings for
   a custom API-key header, sampling parameters, coordinate mode or provider options.
3. **Save configuration** writes `vigil.json` with owner-only file permissions.
   The saved key is never sent back to the browser. An empty key field preserves
   the current key; the explicit remove option clears it. Environment keys can
   still apply. The CLI and UI share validation and configuration precedence.
4. **Check setup** checks local readiness without starting a simulator or calling
   the model. **Test connection** additionally sends one small text request and
   uses API quota. A text connection check alone does not validate image support.
5. The first canonical task is selected initially. Click **Run 1 episode** to
   verify the complete RGB/model/action loop. A new timestamped output directory
   is created under `outputs/` for each evaluation. The run action bar stays visible
   while choosing tasks. Select more tasks once a real episode works.

Task search, family and difficulty filters control the visible list. Selection
is preserved across pages and filters; the run button always shows the total
number selected. **Select filtered tasks** selects the entire filtered set,
including other pages. **Clear selection** removes the whole selection.
Concurrency defaults to one; increase it only after checking rendering capacity.

The evaluation page's **Concurrency and API capacity** section controls simulator
startup and active simulator limits through the same CLI options. Zero means
automatic: up to eight starts and four live simulators, capped by the worker
count. The displayed bound explains how many episodes/model requests can actually
overlap. These controls do not enforce provider requests/tokens-per-minute quotas.

For a separate model settings file, use `vigil ui --config models/vision.json`.
`vigil --config models/vision.json ui` selects the same file. The workbench edits
a file, so `--no-config` is only supported by evaluation commands; it is rejected
by the UI instead of silently reading the default settings.

The workbench launches the public `vigil run` command in a child process. It
retains original episode budgets, the RGB-only profile and the shared scorer.
It does not deploy models, allocate remote machines or add privileged model input.

## Progress, stopping and errors

Final W/B is shown only after a shared evidence audit passes: step-derived
settlements, saved scores and aggregate must agree. **Evidence verified** marks
that internal-consistency check. An error hides final metrics and names the
problem. The **Episodes saved** count is progress, not a successful-task count.
One malformed run is marked invalid without preventing access to other runs.

**Results & replay** refreshes during an active evaluation. **Live view** shows
the latest saved RGB while an episode is running; decisions and judgments become
available in the completed episode trace. W/B appears after the entire selection
finishes without infrastructure errors. Goal failures are valid results.

**Stop run** cancels only the process started by this workbench and cleans up its
episode processes. Completed outputs are retained. Closing the browser tab leaves
the evaluation running; press Ctrl+C in the workbench terminal to stop the server
and its active run. A cancelled or interrupted evaluation does not display old
aggregate scores as final results. Read the process log for errors and consult
the CLI `--resume-existing` workflow for compatible interrupted experiments.

If frames were discarded with `--no-frames`, the replay still shows actions and
judgments and explicitly marks the images unavailable. It never invents frames.

## Open existing results

For offline consistency checks before sharing a result, run
`vigil verify-run /path/to/experiment --require-frames`. This reconstructs
settlements from saved steps and checks scores and aggregate. See
[trajectory analysis](TRACE_ANALYSIS.md) for limitations and failure attribution.

```bash
vigil ui --results-dir outputs
vigil ui --results-dir /path/to/experiment
vigil ui --config models/my-model.json --port 8766
```

`--results-dir` selects an existing directory to **read**. New evaluations use
`--out-dir` (default `outputs/`), and remain discoverable alongside the inspected
results. Browsing `examples/recorded-runs` does not redirect new runs into it.
Temporary credential snapshots are owner-only files outside all run directories
and are removed when the child process exits.

The workbench discovers release-format runs beneath these selected directories. It does not import arbitrary historical formats or expose the entire
filesystem. **Download results** exports the completed aggregate JSON; original
traces and PNGs remain in the output directory.

The wheel includes the UI and recorded demo. Real tasks require the release's
`data/` directory; if you installed the wheel elsewhere, set
`VIGIL_DATA_ROOT=/path/to/release/data`. Missing benchmark data does not prevent
browsing the recorded example.

## Use a remote rendering machine

On the machine with your simulator and model configuration:

```bash
vigil ui --no-open --port 8765
```

From your own computer:

```bash
ssh -L 8765:127.0.0.1:8765 your-machine
```

Open `http://127.0.0.1:8765` locally. The server remains bound to loopback. It
checks request origins and uses a per-session token for configuration changes
and run controls. It is a personal local tool, not a public multi-user service.
